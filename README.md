# Инспектор ИИ

Сверка проектной (ПД), рабочей (РД) и исполнительной (ИД) документации строительного объекта по матрице из
132 параметров. Решение задачи 10 ЛЦТ-2026 (Мосстройнадзор).

Инспектор загружает пакет документов. Сервис находит значения параметров во всех трёх стадиях, сопоставляет их и
собирает протокол по Приложению 2 ТЗ. В протокол попадают кандидаты в нарушения. У каждого кандидата есть
доказательства: файл, SHA-256, страница, рамка на странице и цитата. Инспектор подтверждает или отклоняет кандидатов,
после чего финализирует протокол.

Все модели работают локально, внешние API не используются. Лицензии всех моделей разрешают коммерческое и
государственное использование.

## Возможности

- **Приём пакета:** PDF, DOC/DOCX, XLS/XLSX, RTF, ODT, сканы, архивы zip/7z/rar. Дубликаты отбрасываются, повторно
  загруженный файл не разбирается заново.
- **OCR сканов** с автоматическим выпрямлением повёрнутых страниц.
- **Сверка ПД ↔ РД ↔ ИД** по 132 параметрам: извлечение значений, группировка по локациям, вердикт и повторная
  проверка вердикта.
- **Рабочее место инспектора:** карточка кандидата и страницы трёх стадий рядом, значение на странице подсвечено,
  решения принимаются клавишами.
- **Результат:** протокол в PDF, DOCX и XML, JSON по схеме организаторов, история версий протокола.
- **Дообучение по решениям людей:** классификатор типа страницы учится на правках разметчиков, отбор страниц — на
  решениях экспертов. Новую версию утверждает человек, откатиться можно к любой утверждённой версии.
- **Выборка GOLD** из решений инспекторов, с версиями и разбиением train / validation / test.

## Как это работает

```
браузер ──► api (FastAPI) ──► db (Postgres 16) ◄── worker ──► llm (vLLM, Qwen3.8-27B)
                                                    │
                                                    └─ RapidOCR, классификатор страниц, отбор страниц
```

`worker` выполняет конвейер из 11 этапов:

**приём файлов → страницы → OCR → тип страницы → документы → отбор страниц → перечитывание сканов →
извлечение значений → сопоставление → свободный поиск → протокол.**

Подробнее: [docs/architecture.md](docs/architecture.md).

## Быстрый старт

Нужны Linux x86_64, 1× NVIDIA H100 80 ГБ с драйвером ≥ 580, Docker ≥ 24 с Compose ≥ 2.24 и NVIDIA Container Toolkit,
а также ≥ 100 ГБ на диске. Полные требования и варианты для других GPU — в
[docs/deployment.md](docs/deployment.md).

```bash
git clone https://github.com/VolkovMaxim/inspector-ai.git && cd inspector-ai

cp .env.example .env                      # смените пароли, POSTGRES_PASSWORD и JWT_SECRET до первого запуска
scripts/prefetch_models.sh h100           # веса моделей, ~31 ГБ
docker compose --profile h100 up -d --build

curl -s localhost:8080/health             # "status":"ok", когда llm загрузится (до 15 мин)
```

| Адрес | Что там |
|---|---|
| http://localhost:8080 | веб-интерфейс |
| http://localhost:8080/api/docs | Swagger UI |
| http://localhost:8080/api/v1/openapi.json | спецификация OpenAPI 3 |

Демо-учётки (логин = пароль): `inspector`, `supervisor`, `ml`, `admin` — что каждая умеет, в разделе [Роли](#роли).

## Роли

Роли разделяют ответственность: решения по кандидатам принимают инспектор и супервизор, отменить финализированный
протокол может только супервизор, новую версию модели выпускает ML-инженер, нормативную базу меняет администратор.
Каждое действие пишется в журнал с именем пользователя.

| Учётка | Роль | Зачем нужна | Что может |
|---|---|---|---|
| `inspector` | инспектор | проводит проверку объекта | загружает пакет и запускает проверку; подтверждает или отклоняет кандидатов с причиной; финализирует протокол и отправляет его в ИАИС РиН; исправляет тип страницы; видит журнал отдельной проверки |
| `supervisor` | супервизор | контролирует работу инспекторов | всё, что инспектор; отменяет финализацию протокола с указанием причины; видит журнал действий всех пользователей |
| `ml` | ML-инженер | отвечает за модели сервиса | исправляет тип страницы; собирает версии выборки GOLD и отчёт по дообучению; запускает дообучение классификатора страниц и отбора страниц, утверждает, отклоняет и откатывает их версии; видит журнал действий всех пользователей. Файлы не загружает и по кандидатам не решает: тот, кто выпускает модель, не влияет на решения о нарушениях |
| `admin` | администратор | настраивает сервис | все права; меняет нормативную базу (матрицу 132 параметров); импортирует большие пакеты с диска сервера |

Пароли учёток задаются в `.env` до первого запуска. Подробнее — [docs/usage.md](docs/usage.md#интерфейс-роли-и-демо-учётки).

## Использование

1. Войдите как `inspector` и нажмите «Новая проверка».
2. Разложите файлы по зонам ПД / РД / ИД или выберите «Определить автоматически».
3. Запустите проверку. Прогресс по этапам виден на странице проверки.
4. В рабочем месте подтвердите или отклоните каждого кандидата, затем финализируйте протокол.
5. Выгрузите протокол (PDF / DOCX / XML) или `submission.json`.
6. Войдите как `ml`, откройте «GOLD и дообучение», дообучите классификатор страниц на правках типов, а отбор страниц —
   на решениях по кандидатам, и утвердите новые версии.

Всё то же самое можно сделать через API. Примеры загрузки через curl, импорт больших пакетов с диска сервера и
форматы результатов описаны в [docs/usage.md](docs/usage.md). Примеры выходных файлов лежат в
[examples/](examples/).

## Конфигурация

Все настройки задаются в `.env`. Каждая переменная с пояснением есть в [.env.example](.env.example). Чаще всего
меняют эти:

| Переменная | Назначение |
|---|---|
| `INSPECTOR_PASSWORD`, `SUPERVISOR_PASSWORD`, `ML_PASSWORD`, `ADMIN_PASSWORD` | пароли демо-учёток; действуют только при первом запуске |
| `POSTGRES_PASSWORD`, `JWT_SECRET` | секреты; пустой `JWT_SECRET` заменяется случайным ключом |
| `API_PORT`, `API_BIND` | порт и адрес api на хосте |
| `LLM_MODEL_REPO` | веса Qwen; запасной вариант — `unsloth/Qwen3.8-27B-NVFP4` |
| `IMPORT_DIR` | каталог хоста для импорта больших пакетов |
| `COMPOSE_FILE` | подключает GPU к worker; без этой строки worker работает на CPU |

## Разработка

Для разработки GPU и vLLM не нужны. Тесты используют SQLite и поддельную LLM.

```bash
uv sync --extra dev --extra ocrbox        # Python ≥ 3.11
uv run pytest                             # тесты бэкенда

cd web && npm ci
npm test                                  # тесты интерфейса (vitest)
npm run dev                               # http://localhost:5173, /api проксируется на localhost:8080
```

Для локального запуска без Docker:

```bash
uv run uvicorn inspector.api.app:app --port 8080     # БД — SQLite в ./var
uv run python -m inspector.worker                    # конвейер; модель — LLM_URL (по умолчанию localhost:8000/v1)
```

Прогнать конвейер на папках с диска без интерфейса: `uv run python scripts/run_pipeline.py --help`.

## Структура репозитория

```
inspector/
  api/          REST API /api/v1, авторизация, роли
  pipeline/     этапы конвейера: intake → … → compare
  ml/           классификатор типа страницы, отбор страниц, реестр моделей
  render/       протокол в PDF / DOCX / XML
  resources/    матрица параметров, схема сабмита, веса RapidOCR и отбора страниц
  worker.py     обработчик очереди задач
web/            интерфейс (React + Vite)
model_code/     исходный код классификатора типа страницы
scripts/        скачивание весов, прогон конвейера, сверка хранилища
tests/          pytest; tests/fake_llm.py — поддельная модель
docs/           подробная документация
```
